    Chapter 1 · The mental model

    Git is a save system for folders

    Before any commands: learn the four places your work can live. Almost every confusing Git moment is just "my change is in a different place than I thought."

    Written for Windows. Every instruction and screenshot of output assumes a Windows 10 or 11 PC, with commands typed into Git Bash, the terminal that comes with Git for Windows. Chapter 2 sets it up.

    Git is a program on your computer. It watches one folder (a ) and lets you take named snapshots of it called . You can go back to any snapshot, compare snapshots, and work on several versions at once using .

    GitHub is a website that stores a copy of your repository online. It adds things Git doesn't have: a web page for your code, , issues, and permissions for teammates. Git works fine without GitHub. GitHub doesn't do much without Git.

    The four places

    On your disk

    Working directory

    The actual files you open and edit in your editor. Git notices changes here but doesn't save them by itself.

    Inside .git

    Staging area

    A waiting room. You pick which changes go into the next snapshot. Also called "the index."

    Inside .git

    Local repository

    Every commit you've made, stored permanently in the hidden .git folder on your computer.

    On GitHub

    Remote repository

    A copy of the repository on a server, so others can get it and you have a backup.

    git add →git commit →git push →
    ← git pull

    A typical change travels left to right:

    1. You edit index.html in your editor. The change exists only in the .
    2. git add index.html copies that change into the . Nothing is saved permanently yet.
    3. git commit -m "Fix header" takes everything in the staging area and records it as a commit. Now it's permanent, but only on your computer.
    4. git push uploads your new commits to GitHub, the . Now teammates can see it.
    Why have a staging area at all? Because you often change five things and only want to save three of them together. Say you fixed a bug and also left some debug code in another file. You stage only the bug fix, commit it with a clear message, and keep the debug code out of history.

    What a commit really is

    A commit is a full snapshot of every tracked file at one moment, plus:

    • a message you write ("Add login form")
    • an author and date
    • a pointer to the parent commit that came before it
    • a unique ID called a , like 3f9a2c1

    Because each commit points to its parent, commits form a chain. A branch is just a sticky note with a name (like main) stuck on one commit in that chain. When you commit, the sticky note moves forward to the new commit. That's all a branch is.

    How to use this guide. Words with a dotted underline open a definition when you click them. Every command has a Try button that sends it to the Sandbox, a fake terminal in your browser where you can practice without breaking anything.
    Chapter 2 · One-time setup

    Install Git and tell it who you are

    You do this once per Windows PC. It takes about fifteen minutes.

    Download Git for Windows

    Go to git-scm.com/downloads/win and click Click here to download. That gets the 64-bit installer, which is right for almost every PC.

    Or, if you're comfortable with PowerShell, install it with Windows' built-in package manager:

    winget install --id Git.Git -e
    winget
    The Windows Package Manager, built into Windows 10 and 11. Run this one in PowerShell, not Git Bash (you don't have Git Bash yet).
    install --id Git.Git
    Install the package whose ID is Git.Git, the official Git for Windows.
    -e
    "Exact." Match that ID exactly, so winget doesn't pick a similarly named package.

    Run the installer

    Clicking Next through every screen works. Four screens are worth a second look:

    ScreenPickWhy
    Choosing the default editor used by GitUse Visual Studio Code if you have it, otherwise Use NotepadThe default is Vim, which confuses almost everyone the first time. Git opens this editor when it needs you to type a message.
    Adjusting the name of the initial branchOverride the default branch name and type mainGitHub calls its first branch main. Matching it avoids confusion later.
    Adjusting your PATH environmentKeep Git from the command line and also from 3rd-party softwareLets you use Git in PowerShell, VS Code and other apps too, not only in Git Bash.
    Configuring the line ending conversionsKeep Checkout Windows-style, commit Unix-styleWindows and Mac/Linux end lines differently. This setting stops that from showing up as fake changes when you work with others.

    Leave the credential helper on Git Credential Manager (the default). It handles signing in to GitHub for you, as you'll see in the last step.

    Open Git Bash

    Press the Windows key, type Git Bash, and press Enter. A black window opens. This is your : you type a command, press Enter, and it prints a result.

    What you'll see
    Sam@LAPTOP-4F2K MINGW64 ~
$
    Sam@LAPTOP-4F2K
    Your Windows user name and your PC's name.
    MINGW64
    The name of the system that lets Git Bash run Linux-style commands on Windows. You can ignore it.
    ~
    The folder you're in. ~ means your home folder, C:\Users\Sam.
    $
    The prompt. It means "ready, type a command."
    Why Git Bash and not PowerShell or Command Prompt? Git works in all three, but the other commands in this guide (ls, pwd, echo "text" > file) behave differently or don't exist in Command Prompt, and the PowerShell built into Windows can save echo output in a format Git treats as binary gibberish. Use Git Bash for everything here and every command will work exactly as shown.
    Shortcuts: in File Explorer, open any folder, right-click empty space, and choose Open Git Bash here (on Windows 11, first click Show more options). Git Bash opens already inside that folder. In VS Code, open the terminal with Ctrl + ` and pick Git Bash from the + ▾ menu.

    Learn five terminal commands

    These are not Git commands. They're for moving around folders, and you'll use them constantly.

    cd folder"Change directory." Moves into a folder. cd .. goes up one level. cd ~ goes home. Put names with spaces in quotes: cd "My Projects".cd Documents/blog

    explorer .Opens the current folder in File Explorer, so you can see the same files in the normal Windows way. The . means "this folder."explorer .
    Keyboard in Git Bash: Tab auto-completes file and folder names. ↑ brings back your previous command. To paste, use Shift + Insert or right-click → Paste. Ctrl + C does not copy here: it stops whatever command is running. To copy, select text with the mouse (that copies it automatically).

    Check that Git works

    git --version
    git
    Runs the Git program. Every Git command starts with this word.
    --version
    A . Flags start with dashes and change what a command does. This one just asks Git to print its version.
    What you'll see
    git version 2.47.1.windows.1

    Any version number means you're set. If you see command not found or "'git' is not recognized," close every terminal window, open a new one, and try again. A window that was already open during installation can't see the new program.

    Set your name

    Every commit records who made it. Git refuses to commit until you set this.

    git config --global user.name "Sam Rivera"
    config
    The Git command for reading and changing settings.
    --global
    Save this setting for every repository on this computer, not just the current one.
    user.name
    The name of the setting.
    "Sam Rivera"
    The value. Quotes keep the space from splitting it into two words. Use your real name or a handle; it appears on every commit.
    What you'll see
    (nothing. No output means it worked.)

    Set your email

    git config --global user.email "sam@example.com"
    user.email
    Use the same email as your GitHub account so GitHub links commits to your profile.
    Privacy option: GitHub gives you a no-reply address (Settings → Emails) that looks like 12345+sam@users.noreply.github.com. Use it here if you don't want your real email in public history.

    Name the default branch "main" (if you skipped it in the installer)

    git config --global init.defaultBranch main
    init.defaultBranch
    The name Git gives the first branch in a new repository. Without this, Git uses master, while GitHub uses main. Running it again is harmless if you already picked main in the installer.

    Make sure Git uses an editor you know

    Skip this if you picked VS Code or Notepad in the installer.

    git config --global core.editor "code --wait"
    core.editor
    The program Git opens when it needs you to type something longer, such as a commit message when you forget -m.
    "code --wait"
    Use VS Code, and --wait tells Git to wait until you close that tab. No VS Code? Use "notepad" instead.

    Check your settings

    git config --global --list
    What you'll see
    user.name=Sam Rivera
user.email=sam@example.com

core.editor=code --wait

    Create a GitHub account

    Sign up at github.com/signup. That's all for now. You don't need to sign in from Git Bash yet.

    How signing in works on Windows: the first time you git push or git clone a private repository, Git Credential Manager (installed with Git) opens a small window. Click Sign in with your browser, approve the request on the GitHub page that opens, and you're done. Windows stores the login in Credential Manager, so you won't be asked again.

    Don't type your GitHub password into Git Bash. If Git ever asks for a username and password in the terminal itself, the password won't work: GitHub stopped accepting passwords there in 2021. That prompt means Git Credential Manager isn't set up. Fix it by running git config --global credential.helper manager, then push again.
    Signed in as the wrong GitHub account? Press the Windows key, open Credential Manager → Windows Credentials, remove the entry starting with git:https://github.com, and push again to sign in fresh.

    Optional: the GitHub CLI (gh) lets you do GitHub things like opening pull requests from the terminal. Install it in PowerShell with winget install --id GitHub.cli -e, then run gh auth login in a new Git Bash window. Other ways to sign in are an or a ; both work, but take more steps.

    Chapter 3 · Getting a repository

    Two ways to start: new or copied

    Either you turn a folder on your computer into a repository (git init), or you download one that already exists on GitHub (git clone).

    Option A: a brand-new project

    Make a folder and move into it

    mkdir my-project
    cd my-project

    Git works on whichever folder your terminal is in. Being in the wrong folder is the #1 beginner mistake. Run pwd if you're unsure. A good home for projects is a folder like C:\Users\Sam\projects: in Git Bash, mkdir ~/projects once, then cd ~/projects before creating each project.

    Turn it into a repository

    git init
    init
    "Initialize." Creates a hidden folder called .git inside the current folder. That hidden folder is the repository: all commits, branches, and settings live there.
    What you'll see
    Initialized empty Git repository in C:/Users/Sam/projects/my-project/.git/

    You won't see .git in File Explorer because it's hidden. To show it: File Explorer → View → Show → Hidden items (on Windows 10: View tab → tick Hidden items). Don't edit anything inside it by hand.

    Don't run git init in your home folder (C:\Users\Sam), Desktop, Documents, or OneDrive. It would make Git track everything there. If you did it by accident, delete the .git folder that it created (rm -rf .git in that folder) and nothing else is affected.
    Avoid OneDrive folders. If your Documents or Desktop syncs to OneDrive, keep repositories somewhere else, like C:\Users\Sam\projects. OneDrive syncing files inside .git while Git is writing them can corrupt the repository.

    Confirm it worked

    git status
    What you'll see
    On branch main

No commits yet

nothing to commit (create/copy files and use "git add" to track)

    git status is the command you'll run most. It answers "where are my changes right now?" When in doubt, run it.

    Option B: copy an existing project from GitHub

    Get the repository's URL

    On the repository's GitHub page, click the green Code button and copy the HTTPS URL. It ends in .git.

    Clone it

    git clone https://github.com/octo-org/website.git
    clone
    Downloads the whole repository, including every past commit, into a new folder named after the repo (website).
    https://…git
    Where to download from. Git automatically remembers this address under the name , so git push and git pull know where to go later.
    What you'll see
    Cloning into 'website'...
remote: Enumerating objects: 412, done.
Receiving objects: 100% (412/412), 1.2 MiB | 4.1 MiB/s, done.
Resolving deltas: 100% (198/198), done.

    Move into the new folder

    cd website

    Clone creates a folder but leaves you outside it. Git commands won't work until you cd in.

    Which do I use? Starting from scratch → init. The code already exists on GitHub (yours, your team's, or open source) → clone. Never both in the same folder.
    Chapter 4 · Status, add, commit

    The loop you'll repeat a thousand times

    Edit → git status → git add → git commit. Master this and you know 80% of daily Git.

    Make a change

    Create or edit a file in your editor. In the terminal you can create one quickly:

    echo "Buy milk" > notes.txt
    echo "Buy milk"
    Prints the text. (Not a Git command; it's a basic terminal command.)
    > notes.txt
    Sends that text into a file named notes.txt instead of the screen, creating or overwriting it. >> adds to the end instead of overwriting.

    Ask Git what changed

    git status
    What you'll see
    On branch main

No commits yet

Untracked files:
  (use "git add <file>..." to include in what will be committed)
	notes.txt

nothing added to commit but untracked files present

    means Git sees the file but has never saved it. Git ignores untracked files until you add them. Notice that Git prints hints telling you the next command. Read them; they're usually right.

    Stage the change

    git add notes.txt
    add
    Copies the file's current contents into the staging area, marking it for the next commit.
    notes.txt
    Which file. You can list several: git add a.txt b.txt.

    Then run git status again:

    What you'll see
    Changes to be committed:
  (use "git rm --cached <file>..." to unstage)
	new file:   notes.txt
    Seeing "LF will be replaced by CRLF"? Git on Windows may print warning: in the working copy of 'notes.txt', LF will be replaced by CRLF the next time Git touches it. It's harmless. Windows and Mac/Linux end lines with different invisible characters, and Git is telling you it's converting them so the file looks right on everyone's computer.
    Shortcuts: git add . stages every change in the current folder and below. Handy, but run git status first so you don't stage something you didn't mean to. git add -p walks you through each changed chunk and asks yes/no, which is great for committing only part of a file.
    Important: git add stages the file as it is right now. If you edit it again afterward, the new edit isn't staged. git status will show the file in both "to be committed" and "not staged" lists. Just git add it again.

    Commit

    git commit -m "Add shopping notes"
    commit
    Saves everything in the staging area as a new snapshot.
    -m
    "Message." The text right after it becomes the commit message.
    "Add shopping notes"
    The message. Write it so someone reading the history later knows what this commit does.
    What you'll see
    [main (root-commit) 3f9a2c1] Add shopping notes
 1 file changed, 1 insertion(+)
 create mode 100644 notes.txt

    Reading that output: main is the branch, root-commit means it's the very first commit, and 3f9a2c1 is the short , this commit's ID.

    Forgot -m? Git opens a text editor (often Vim) for you to type the message. If you set VS Code or Notepad in setup, it opens there: type the message on the first line, save, and close the tab or window. If you're stuck in Vim (a black screen with ~ down the side): press i, type your message, press Esc, type :wq, press Enter. Then set a friendlier editor (see setup).

    Edit, then commit again in one move

    git commit -am "Add eggs to list"
    -a
    "All." Stages every change to files Git already tracks, then commits. It skips new (untracked) files, so you still need git add for those.
    -am
    -a and -m squished together. Single-letter flags can be combined.

    Writing good commit messages

    WeakBetterWhy
    stuffAdd password reset emailSays what the commit does.
    fixed bugFix crash when cart is emptyNames which bug.
    Added files and changed header and fixed typoThree separate commitsOne idea per commit makes it easy to undo one thing.

    Convention: start with a verb in the imperative ("Add," "Fix," "Remove"), keep the first line under about 50 characters. Read it as "If applied, this commit will add password reset email."

    How often to commit? Whenever you reach a point you'd be sad to lose, or finish one small idea. Several times an hour is normal. Small commits are easier to understand and undo.
    Chapter 5 · log, diff, show

    See what changed, and when

    These commands only read. They can't break anything, so experiment freely.

    List commits

    git log --oneline
    log
    Shows commit history, newest first.
    --oneline
    One short line per commit: short hash + message. Without it you get author, date, and full hash too.
    What you'll see
    a71d0e4 (HEAD -> main) Add eggs to list
3f9a2c1 Add shopping notes

    → main means "you're on the main branch, and it's at this commit." If the log is long, Git shows it in a pager: use arrow keys to scroll and press q to quit.

    See every branch as a graph

    git log --oneline --graph --all
    --graph
    Draws lines on the left showing how branches split and join.
    --all
    Include every branch, not just the one you're on.
    What you'll see
    *   c02e9b1 (HEAD -> main) Merge branch 'dark-mode'
|\
| * 8e1f4aa (dark-mode) Add dark theme colors
* | 51b7d20 Fix footer link
|/
* a71d0e4 Add eggs to list

    See unstaged changes, line by line

    git diff
    diff
    Compares your working directory to the staging area: what you've changed but not yet staged.
    What you'll see
    diff --git a/notes.txt b/notes.txt
--- a/notes.txt
+++ b/notes.txt
@@ -1,2 +1,2 @@
 Buy milk
-Buy eggs
+Buy a dozen eggs

    Lines starting with - were removed, + were added. A changed line shows as one removed and one added. a/ is the old version, b/ the new.

    See staged changes

    git diff --staged
    --staged
    Compares the staging area to the last commit: exactly what git commit would save right now. Run this before committing to double-check.

    Inspect one commit

    git show a71d0e4
    show
    Prints one commit's message, author, date, and diff.
    a71d0e4
    The commit's hash. You only need the first 7 or so characters. HEAD means the current commit; HEAD~1 means one before it; HEAD~3 three before.
    On GitHub: click the "commits" count on a repository page to see the same history, and click any commit to see its diff in color.
    Chapter 6 · branch, switch, merge

    Work on something without breaking main

    A branch is a separate line of commits. You try an idea there; if it works you merge it into main, and if not you delete it. Main stays safe the whole time.

    Remember: a branch is a sticky note pointing at a commit. Creating one is instant and costs nothing. is just the branch that, by agreement, holds the working version.

    See your branches

    git branch
    What you'll see
    * main

    The * marks the branch you're on.

    Create a branch and switch to it

    git switch -c dark-mode
    switch
    Moves you to another branch. Your files change to match that branch's latest commit.
    -c
    "Create." Make the branch first, starting from the commit you're on now.
    dark-mode
    The branch name. Use short, dash-separated names that describe the work: fix-login-crash, add-search. Teams often prefix them: feature/search.
    What you'll see
    Switched to a new branch 'dark-mode'
    Older tutorials use git checkout -b dark-mode. It does the same thing. switch was added in 2019 because checkout does too many unrelated jobs.

    Commit on the branch as usual

    echo "body { background: black }" > style.css
    git add style.css
    git commit -m "Add dark theme colors"

    This commit exists only on dark-mode. If you switch to main, style.css disappears from your folder. It isn't deleted; it's waiting on the other branch. Switch back and it reappears.

    Go back to main

    git switch main
    If Git refuses with "Your local changes would be overwritten," you have uncommitted edits that clash with the other branch. Commit them, or set them aside with git stash (see Undo).

    Merge the branch into main

    git merge dark-mode
    merge
    Brings the commits from the named branch into the branch you're currently on. So: switch to the branch that should receive the work, then merge the other one in.
    What you'll see (simple case)
    Updating a71d0e4..8e1f4aa
Fast-forward
 style.css | 1 +
 1 file changed, 1 insertion(+)

    means main had no new commits of its own, so Git just slid the main sticky note forward. If main did get new commits meanwhile, Git creates a merge commit with two parents, tying both lines together. Either way, you don't have to do anything different.

    If both branches changed the same lines, you get a . That's normal and fixable: see Merge conflicts.

    Delete the finished branch

    git branch -d dark-mode
    -d
    "Delete." Removes the sticky note, not the commits; they're part of main now. Git refuses if the branch has unmerged work. -D (capital) forces it, throwing that work away.
    Chapter 7 · remote, push, pull

    Put your repository on GitHub

    You'll connect your local repository to an empty one on GitHub, upload your commits, and then keep the two in sync.

    Create an empty repository on GitHub

    1. On github.com, click + (top right) → New repository.
    2. Name it (e.g. my-project). Choose Public or Private.
    3. Leave "Add a README," ".gitignore," and "license" unchecked. You already have a local project, and those would create a commit on GitHub that your computer doesn't have, causing a rejected push.
    4. Click Create repository. GitHub shows a page of setup commands; the URL there is what you need.

    Tell your local repository where GitHub is

    git remote add origin https://github.com/samrivera/my-project.git
    remote add
    Saves a nickname for a remote repository's URL.
    origin
    The nickname. origin is the standard name for "the main copy on GitHub." You could call it anything, but don't.
    https://…git
    The URL GitHub showed you.

    Check it with git remote -v (v = verbose). You should see the URL twice, once for fetch and once for push.

    Push for the first time

    git push -u origin main
    push
    Uploads your local commits to the remote.
    -u
    Short for --set-upstream. Links your local main to GitHub's main so in future a bare git push or git pull knows where to go. You only need it the first time you push each branch.
    origin
    Which remote to push to.
    main
    Which branch to push.
    What you'll see
    Enumerating objects: 6, done.
Writing objects: 100% (6/6), 512 bytes | 512.00 KiB/s, done.
To https://github.com/samrivera/my-project.git
 * [new branch]      main -> main
branch 'main' set up to track 'origin/main'.

    Refresh the GitHub page: your files and commits are there.

    "error: src refspec main does not match any" means you haven't made a commit yet (or your branch is called master). Commit first, or rename with git branch -M main.

    From now on: commit, then push

    git push

    Commits stay on your computer until you push. A good habit: push at the end of every work session, so GitHub is also your backup.

    Get changes others pushed

    git pull
    pull
    Two steps in one: (download new commits from GitHub) then merge them into your current branch.
    What you'll see
    Updating a71d0e4..d4c88f0
Fast-forward
 README.md | 3 +++
 1 file changed, 3 insertions(+)
    Habit: git pull before you start work each day, and before you create a new branch. You'll start from the latest version and get fewer conflicts.

    When a push is rejected

    What you might see
     ! [rejected]        main -> main (fetch first)
error: failed to push some refs to 'https://github.com/samrivera/my-project.git'
hint: Updates were rejected because the remote contains work that you do not
hint: have locally.

    Someone (maybe you, on another computer, or via the GitHub website) pushed commits you don't have. Git won't let you overwrite them. Fix: git pull, resolve any conflicts, then git push again.

    Never "fix" this with git push --force on a shared branch. It replaces GitHub's history with yours and deletes your teammates' commits.

    fetch vs. pull

    CommandDownloads new commits?Changes your files?Use when
    git fetchYesNoYou want to look before mixing anything in. Then compare with git log main..origin/main.
    git pullYesYes (merges)You just want to be up to date. Most of the time.

    After a fetch, GitHub's version of main is visible locally as origin/main, a read-only bookmark of where main was on GitHub the last time you checked.

    Chapter 8 · Team workflow

    The pull request workflow

    This is how almost every team and open-source project works. Nobody commits straight to main. Each change goes on a branch, then a pull request asks for it to be reviewed and merged.

    A (PR) is a page on GitHub that says "please merge my branch into main." It shows the diff, runs automated checks, and lets people comment on specific lines before anything is merged.

    Start from an up-to-date main

    git switch main
    git pull

    Create a branch for this one change

    git switch -c fix-signup-typo

    One branch per task. Small PRs get reviewed faster and are easier to undo.

    Make your change and commit

    git add signup.html
    git commit -m "Fix typo in signup button"

    Several commits on the branch are fine.

    Push the branch

    git push -u origin fix-signup-typo

    Same as before, but pushing your new branch instead of main. GitHub's reply even includes a link to open the PR:

    What you'll see
    remote: Create a pull request for 'fix-signup-typo' on GitHub by visiting:
remote:   https://github.com/samrivera/my-project/pull/new/fix-signup-typo

    Open the pull request on GitHub

    1. Open that link, or visit the repository and click the yellow Compare & pull request banner.
    2. Check the top: base: main ← compare: fix-signup-typo. Base is where it's going; compare is what you're bringing.
    3. Write a title and a description: what changed, why, and how to test it. Screenshots help for visual changes.
    4. Click Create pull request. If you want early feedback before it's done, use the arrow next to the button to choose Create draft pull request.

    Or from the terminal with the GitHub CLI: gh pr create --fill.

    Review and update

    Reviewers leave comments and either Approve or Request changes. To address feedback, just keep working on the same branch locally, commit, and git push. The PR updates automatically. Don't open a new PR.

    The Checks section shows automated tests (often called ). A red ✗ means something failed; click Details to see why.

    Merge

    Once approved, click the green merge button. It has three modes in its dropdown:

    OptionWhat happens
    Create a merge commitKeeps all your branch's commits plus a merge commit. Full detail.
    Squash and mergeCombines all your branch's commits into one commit on main. Tidy history; the most popular choice.
    Rebase and mergeReplays your commits onto main one by one, with no merge commit. Linear history.

    Use whichever your team uses. Then click Delete branch on the PR page to remove the remote branch.

    Clean up locally

    git switch main
    git pull
    git branch -d fix-signup-typo

    Your main now includes the merged change. If the PR was squashed, -d may complain the branch "is not fully merged" because the commit IDs differ; since GitHub shows it merged, git branch -D is safe here.

    Contributing to someone else's project: forks

    You can't push branches to a repository you don't have write access to. Instead you it: click Fork on its GitHub page to make your own copy under your account. Clone your fork, branch, commit, push to your fork, then open a PR from your fork to the original. GitHub's PR page lets you pick the original repository as the base.

    To keep your fork current, add the original as a second remote, conventionally called upstream:

    git remote add upstream https://github.com/original-owner/project.git
    git pull upstream main
    Chapter 9 · Fixing things

    Undo almost anything

    Find your situation below. The key question is always: has this been pushed yet? Rewriting local, unpushed history is fine. Rewriting pushed history causes problems for everyone else.

    SituationCommandSafe?
    Edited a file, want the last committed version backgit restore file.txtDiscards your edits for good
    Staged something by mistakegit restore --staged file.txtYes, keeps your edits
    Typo in the last commit message, or forgot a file (not pushed)git commit --amendOnly if not pushed
    Undo the last commit but keep its changes (not pushed)git reset --soft HEAD~1Only if not pushed
    Undo a commit that's already pushedgit revert <hash>Yes, always
    Need to switch branches but work isn't ready to commitgit stash … git stash popYes
    Throw away everything since the last commitgit reset --hardDestroys uncommitted work
    "I lost a commit" after a bad resetgit reflogYes, read-only

    Discard changes to a file

    git restore notes.txt
    restore
    Puts the file back the way it was at the last commit (or the staged version, if you staged it). Your unsaved edits are gone; Git never recorded them, so there's no getting them back.

    Unstage a file

    git restore --staged notes.txt
    --staged
    Only touch the staging area. The file leaves the waiting room, but your edits stay in the file.

    Fix the last commit

    git add forgotten-file.txt
    git commit --amend -m "Add notes and forgotten file"
    --amend
    Replaces the last commit with a new one that includes whatever's staged now, with the new message. It gets a new hash, which is why you shouldn't amend something already pushed.

    Reverse a pushed commit

    git revert 8e1f4aa
    revert
    Creates a new commit that does the exact opposite of the given commit. History stays intact (the mistake and its undo are both visible), so it's safe on shared branches. Git opens an editor for the message; save and close to accept the default.

    Undo commits locally

    git reset --soft HEAD~1
    reset
    Moves your branch's sticky note back to an earlier commit.
    --soft
    Keep the changes from the undone commit, staged. Use this to redo a commit differently.
    HEAD~1
    One commit before the current one. HEAD~2 would undo two.
    The three modes of reset: --soft keeps changes staged · --mixed (the default) keeps changes but unstaged · --hard deletes the changes completely. Use --hard only when you're sure.

    Put work aside temporarily

    git stash
    stash
    Saves your uncommitted changes onto a hidden shelf and cleans your working directory back to the last commit. Now you can switch branches, pull, whatever.
    git stash pop
    pop
    Takes the most recent stash off the shelf and reapplies it. git stash list shows everything on the shelf.

    Find "lost" commits

    git reflog
    reflog
    "Reference log." A diary of every place HEAD has pointed recently, even commits no branch points to anymore. Find the hash from before your mistake, then git switch -c rescue <hash> to put a branch on it.
    What you'll see
    a71d0e4 HEAD@{0}: reset: moving to HEAD~1
c02e9b1 HEAD@{1}: commit: Add search page   ← this is the one you "lost"
a71d0e4 HEAD@{2}: commit: Add eggs to list
    Reassuring fact: once something is committed, it's very hard to truly lose it. Uncommitted work is what's fragile. Commit often.
    Chapter 10 · Conflicts

    Resolve a merge conflict calmly

    A conflict happens when two branches changed the same lines differently and Git can't guess which to keep. It stops and asks you. Nothing is broken, and nothing is lost.

    Recognize it

    After git merge or git pull
    Auto-merging notes.txt
CONFLICT (content): Merge conflict in notes.txt
Automatic merge failed; fix conflicts and then commit the result.

    See which files are affected

    git status
    What you'll see
    You have unmerged paths.
  (fix conflicts and run "git commit")
  (use "git merge --abort" to abort the merge)

Unmerged paths:
	both modified:   notes.txt

    Open the file and read the markers

    Inside notes.txt
    Buy milk
<<<<<<< HEAD
Buy a dozen eggs
=======
Buy free-range eggs
>>>>>>> shopping-update
    <<<<<<< HEAD
    Start of your version: the branch you're on.
    =======
    The dividing line.
    >>>>>>> shopping-update
    End of their version: the branch you're merging in.

    Edit the file to what it should be

    Keep yours, keep theirs, or combine them. Then delete all three marker lines.

    Fixed notes.txt
    Buy milk
Buy a dozen free-range eggs
    VS Code highlights conflicts and shows clickable buttons: "Accept Current Change," "Accept Incoming Change," "Accept Both Changes." Current = yours, incoming = theirs.

    Mark it resolved and finish the merge

    git add notes.txt
    git commit -m "Merge shopping-update"

    Here git add means "I've resolved this file." Once every conflicted file is added, the commit completes the merge.

    Or back out entirely

    git merge --abort

    Returns everything to how it was before you ran merge. Useful when you need to think or ask a teammate.

    Fewer conflicts: pull often, keep branches short-lived (days, not weeks), and keep PRs small. Conflicts grow with the time two branches spend apart.

    Want to practice? The Sandbox produces real conflicts: change the same file differently on two branches, then merge.

    Chapter 11 · Keeping files out

    Tell Git what never to track

    Passwords, huge build folders, and your OS's junk files shouldn't go into history. A file named .gitignore lists them.

    Create .gitignore in the top folder of your repository

    A typical .gitignore
    # Secrets — never commit these
.env
*.pem

# Dependencies (re-downloadable)
node_modules/
venv/

# Build output
dist/
build/

# Windows and editor junk
Thumbs.db
desktop.ini
.vscode/
    .env
    An exact file name, ignored in any folder.
    *.pem
    * matches anything, so: every file ending in .pem.
    node_modules/
    A trailing slash means a folder and everything in it.
    # …
    Lines starting with # are comments.

    Commit the .gitignore itself so your teammates get the same rules. GitHub keeps templates for most languages at github.com/github/gitignore.

    Already committed a file you meant to ignore?

    Adding it to .gitignore won't remove it; Git keeps tracking files it already knows. Untrack it, keeping your local copy:

    git rm --cached .env
    rm
    Removes a file from Git.
    --cached
    Only from Git's tracking, not from your disk.
    git commit -m "Stop tracking .env"
    If a password or API key was pushed to GitHub, treat it as leaked even after you remove it: it's still in the history and may have been scraped. Revoke it and make a new one at the service that issued it.
